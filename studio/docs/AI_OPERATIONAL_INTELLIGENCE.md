# AI Operational Intelligence

## Doel
AI Operational Intelligence definieert hoe de factory excellent opereert: met meetbare discipline, extreme helderheid, herbruikbare kennis, lage tokenverspilling, sterke releasekwaliteit en snelle learning loops.

## Operating Principles
| Principle | Meaning |
| --- | --- |
| Extreme clarity | Every project, signal, decision and release has owner, state and next action |
| Extreme modularity | Systems are split by responsibility and promoted to shared only with evidence |
| Extreme scalability | Architecture anticipates growth without premature runtime complexity |
| Extreme AI efficiency | Agents use compact context, reusable prompts and measured token budgets |
| Extreme discipline | Gates, branches, releases and incidents are auditable |
| Extreme reuse | Successful patterns become default assets |
| Extreme learning velocity | Incidents, launches and experiments update the system |
| Extreme documentation quality | Docs are control surfaces, not archive pages |
| Extreme release quality | Releases ship with rollback, monitoring and changelog |

| KPI | Target Direction | Intervention |
| --- | --- | --- |
| Launch readiness | above 80 before release | release hold and blocker removal |
| Project health | upward trend | Project Control review |

| Gate blocker recurrence | decreasing | upstream prevention |
| Deployment failure rate | decreasing | release pipeline strengthening |
| Automation coverage | increasing | automation roadmap |
| Prompt success rate | increasing | Prompt Vault promotion/deprecation |
| Reuse rate | increasing | pattern indexing |
| Revenue validation rate | increasing | experiment discipline |
| Documentation health | above 70, preferably 85+ | Knowledge Agent task |

## Scaling Thresholds
| Signal | Threshold | Required Action |
| --- | --- | --- |
| More than 3 active project launches | portfolio prioritization cadence |
| Same pattern used in 3 projects | promote to shared reference |
| Same bug class twice | create prevention rule |
| Branch older than agreed operating window | review scope and split |
| Gate blocker repeats | strengthen upstream pipeline |
| Token cost grows faster than task value | prompt budget review |
| API instability affects release | fallback or provider decision |
| Manual workflow repeated 3 times | automation candidate |

## Optimization Cycles
### Daily / Per Work Session
- review active signals;
- confirm blocked work;
- update high-impact graph nodes;
- keep documentation and changelog aligned with meaningful changes.

### Weekly
- rank project priorities;
- inspect token and agent performance;
- review launch readiness;
- promote or retire reusable patterns;
- identify automation candidates.

### Per Release
- validate gates;
- confirm rollback;
- observe telemetry;
- record outcome;
- extract learning.

### Monthly
- evaluate portfolio strategy;
- identify cross-project intelligence;
- review governance violations;
- update operating standards.

## Performance Standards
| Area | Standard |
| --- | --- |
| Documentation | Current, decision-oriented, linked to execution |
| Agent work | Contracted, scored, confidence-rated |
| Release | Gated, rollback-ready, observed |
| API | Registry-controlled with retries, rate limits and fallback |
| Security | No secrets in repo, explicit review for sensitive flows |
| UX | Mobile-first, error states, loading states, conversion clarity |
| Analytics | Metrics defined before conclusions |
| Token usage | Budgeted, measured and optimized |

## Bottleneck Analysis
The Control Plane should continuously detect:
- too much work in review;
- repeated missing context;
- unstable API dependencies;
- unclear ownership;
- oversized branches;
- low-confidence agent outputs;
- repeated release blockers;
- missing telemetry for decisions.

## Excellence Model
Operational excellence is reached when the factory can answer these questions immediately:
- What should be built next and why?
- Which release is blocked and by which gate?
- Which project has the highest revenue-adjusted readiness?
- Which repeated bug deserves a prevention rule?
- Which prompt wastes tokens?
- Which architecture pattern is ready for reuse?
- Which API is too unstable for launch?
- Which automation will remove the most manual effort?
